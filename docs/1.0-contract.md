# ScarletUI application and extension contract

Status: current-behavior baseline for the coordinated 1.0 release, adopted on
2026-09-06. This document does not publish 1.0, certify every backend, or replace
release-candidate verification. It completes the application/extension boundary
alongside the normative [architecture](ARCHITECTURE.md) and
[frame-failure contract](FRAME_FAILURES.md).

## Public surface and compatibility

The application surface is `scarlet-ui`, its prelude and public reexports:
views/modifiers, layout and event types, `State`, scenes, window commands,
`Application`, and the construction/derive macros. The public core APIs used to
implement custom views, elements, render objects, and platform/paint backends
are extension APIs, not automatically private because they live in another
crate. `pub(crate)` implementation details and explicitly doc-hidden macro
plumbing such as `__private` are not extension points.

Within a released major version, preserve supported public signatures, generic
bounds, fields, variants, feature names, macro syntax and documented semantics.
Adding a required trait method, changing an exposed dependency type, or adding
a variant to an exhaustive public enum can break consumers. Such changes need
an explicit compatibility/version decision; this baseline does not require a
blanket enum-annotation migration. A default trait method is compatible only
when its default preserves existing implementations' behavior.

There is no stable Rust binary ABI. Build the UI and its Rust dependencies with
compatible sources and toolchains. SGFX's IR/backend/codegen are a coordinated
driver implementation, with Vulkan C ABI the intended future external graphics
boundary. That policy does not exempt ScarletUI's public application or
extension types: changing SGFX underneath a public renderer signature still
requires adapting that signature compatibly or an explicit UI migration.

Preview is a development tool. Its Rust dylib and host must use the same
toolchain and compatible dependency set; it is not an independently versioned
runtime plugin ABI. It does not impose dynamic loading on SGFX applications.

## Build configurations

| Facade features | Intended use |
| --- | --- |
| default (`std`) | Portable UI/core API, without selecting an application platform |
| `std,platform-winit` | Native host application; `platform-winit` implies `std` and the platform's SGFX renderer |
| `std,platform-sws` | Normal Scarlet Rust std application, on `target_os = "scarlet"` |
| `legacy-scarlet-std,platform-sws`, defaults disabled | Legacy Scarlet runtime integration |
| `preview` | Host development support; implies `std`, not platform selection |

Select exactly one runtime mode (`std` or `legacy-scarlet-std`) and at most one
platform. `platform-sws` is Scarlet-only; `platform-winit` is non-Scarlet-only.
`ApplicationRunExt::run` requires the selected platform and `Application + View`.
Custom integrations can supply a `PlatformBackend` to `ApplicationRunner`.
An all-features build is not a supported recipe. Feature availability is not a
claim that every host, compositor, device or optional operation is supported.

## View and State lifetime

The architecture contract remains authoritative: View values are short-lived
descriptions; compatible concrete type and key retain an Element and its runtime
state. Unkeyed siblings are positional; keyed siblings require unique keys.
Replacing/removing a branch ends its retained lifetime. Render objects own
layout/paint state, not the application's durable model.

Cloned `State<T>` values share storage and identity. `set`/`update` notify
subscribers even when the resulting value compares equal; there is no implicit
equality test. Changes invalidate the relevant work, not necessarily an entire
tree or an immediately presented frame. Subscription callbacks are synchronous;
their dispatch is not a reentrant notification queue. Do not recursively mutate
the same State or change its subscriptions from its notification callback.

Application snapshots are cloned into scene roots. Ordinary copied fields do
not become reactive or shared by cloning an application; use shared `State`
and declare the appropriate dependencies. Derived reusable views need
`#[view(body = ...)]`; a bodyless application-state derive is valid for the
runner, but mounting it directly as a reusable component is an error.

## Scene declarations and runtime windows

`SceneWindowKey` identifies a declaration. `WindowId` identifies one live
runtime instance, with its own pipeline and platform window. They are not
interchangeable; numeric IDs are not persistent storage or wire identities.

The current launch/open/close rules are intentional parts of this baseline:

| Operation | Observable behavior |
| --- | --- |
| Direct `Window` scene | Uses its explicit scene key or `main`; launch-eligible by default; honors `open_at_launch` |
| `WindowGroup::new(key, window)` | Uses the group's key and is launch-eligible, regardless of the wrapped Window's key/launch flag |
| Runner startup | Calls `init`, collects declarations in order, rejects duplicate keys, and automatically opens **only the first** launch-eligible declaration |
| `open_window(key)` | Queues creation only if no live instance has that key; existing instances are left alone, not focused |
| `open_new_window(key)` | Queues a fresh WindowId/pipeline even if the same scene already has an instance |
| Unknown key | Open/new/dismiss are no-ops when processed |
| `dismiss_window(key)` | Closes **all** matching instances and bypasses the user-close veto hook |
| User close request | Calls `on_window_close_requested`; `false` keeps the instance alive |

Commands are deferred and processed in queue order by the runner; returning
from the command function is not a creation/close acknowledgment. The queue is
process-global, so concurrent independent application runners are not a
supported isolation boundary. In the default exit mode, zero startup windows
ends the runner before processing commands queued by `init`; likewise closing
the last window can end the loop before another pending command is processed.
Use a launch-eligible scene or explicitly keep the runner alive with
`exit_when_all_windows_closed() == false`.

Declaring, adding or removing a Scene is not automatic platform-window
creation/destruction. Open commands resolve the current declarations. Existing
scene roots rebuild their content for their key; a missing key removes the
content, not the platform window. Duplicate keys are invalid throughout the
application lifetime: startup/command collection returns an error, while the
current content resolver treats failed collection as missing content.

`is_primary` is assigned at creation when no other instance is open, not a
permanent `main` key association. Closing it does not promote another window.
`on_window_created` runs after initial layout, platform creation/size negotiation
and paint-backend acquisition, before its first presentation. It may also run
for command-created windows after startup. Normal final-window exit calls
`on_shutdown`; error returns do not promise that hook. Pipeline teardown still
ends retained subscriptions and runtime state. Close errors are not surfaced
through the fire-and-forget dismiss command.

## Extension responsibilities

- A custom `View` supplies its concrete identity, clone behavior, key and State
  dependencies consistently. Its Element must follow the architecture's update,
  mount/unmount, invalidation and retained-child ownership rules.
- `PlatformBackend` supplies platform defaults and creates windows from the
  requested description. A platform may negotiate a different size; the runner
  applies the returned size before presenting.
- `PlatformWindow` exposes observed state separately from requests. A successful
  resize/fullscreen/focus/pointer-lock request is not confirmation that the
  compositor has applied it. Unsupported optional operations use their existing
  documented defaults or errors; do not synthesize a confirmed capability.
- `take_paint_backend` transfers an optional backend to the window's pipeline.
  Without one, the CPU path calls `present_with_damage`, whose default delegates
  to `present`. Frame-callback support is optional; the fallback event/timer path
  remains valid. No fixed frame interval is guaranteed.
- `PaintBackend::render` returns a CPU buffer borrowed for its declared lifetime
  or a successfully submitted external frame. It must not report a dropped or
  partly accepted frame as successful `External` presentation. Device admission,
  retirement and recovery obey the frame-failure contract.

`on_frame_presented` observes successful submission through that presentation
path, not physical scanout, a transferable GPU completion receipt, or SWS buffer
release. Busy/Rejected/RecoveryRequired keep their existing distinct rules;
there is no automatic device-loss reconstruction, raw-prefix replay, or promise
to stream arbitrarily large scenes. Pixel-identical cross-host rendering,
constant frame rate and unconditional zero allocation are not guarantees.

## Contract evidence

`application::tests::scene_contract_*` checks first-eligible launch, duplicate
key rejection, command reuse/new-instance identity, unknown keys, close veto
versus dismissal, and WindowGroup policy using the existing in-process test
backend. The architecture/State and frame-failure suites remain the evidence
for reconciliation and discard behavior; these new tests do not replace GPU,
compositor, fault/reset or release-candidate tests.
